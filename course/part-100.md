## Common Mistakes and Anti-Patterns

### ❌ Mistake 1: Distributed Monolith

```typescript
// BAD: Service เรียกกันโดยตรง เยอะเกินไป
// OrderService → UserService → InventoryService → PricingService → PaymentService
// ทุก service down = ทั้งระบบ down

// GOOD: ใช้ Saga + Event-Driven
// OrderService publish OrderCreated event
// InventoryService, PaymentService listen and react independently
```

### ❌ Mistake 2: Chatty Services

```typescript
// BAD: เรียก API หลายครั้งเพื่อ render หน้าเดียว
const user = await userService.getUser(id);           // 1 request
const orders = await orderService.getOrders(id);     // 1 request
const preferences = await prefService.getPrefs(id); // 1 request

// GOOD: GraphQL Federation หรือ BFF aggregation
const data = await bffService.getUserDashboard(id); // 1 request
```

### ❌ Mistake 3: Shared Database

```typescript
// BAD: หลาย service อ่าน/เขียน database เดียวกัน
// → tight coupling, ไม่ scale ได้อิสระ

// GOOD: Database per service + integration via events
// OrderDB (PostgreSQL) + UserDB (PostgreSQL) + CatalogDB (MongoDB)
// → communicate via Kafka events
```

### ❌ Mistake 4: Synchronous Everything

```typescript
// BAD: ทุก operation รอ response
await paymentService.processPayment(order);     // blocking
await emailService.sendConfirmation(order);     // blocking
await inventoryService.reserveItems(order);     // blocking

// GOOD: Async where possible
await kafkaProducer.send('order.created', order); // fire-and-forget
// Other services handle asynchronously
```

### ❌ Mistake 5: No Observability

```typescript
// BAD: ไม่มี logs, metrics, tracing
async function processOrder(orderId: string) {
  const order = await db.findOrder(orderId);
  await payment.charge(order);
  return order;
}

// GOOD: Full observability
async function processOrder(orderId: string) {
  const span = tracer.startSpan('processOrder', { attributes: { orderId } });
  const timer = orderProcessingDuration.startTimer({ service: 'order' });

  try {
    logger.info('Processing order', { orderId, traceId: span.spanContext().traceId });
    const order = await db.findOrder(orderId);
    await payment.charge(order);
    orderProcessedTotal.inc({ status: 'success' });
    span.setStatus({ code: SpanStatusCode.OK });
    return order;
  } catch (error) {
    orderProcessedTotal.inc({ status: 'error' });
    span.recordException(error as Error);
    span.setStatus({ code: SpanStatusCode.ERROR });
    throw error;
  } finally {
    timer();
    span.end();
  }
}
```

## Interview Q&A: 30 ข้อสำคัญ

### Fundamentals

**Q1: Microservices vs Monolith เลือกอะไร เมื่อไหร่?**

```
ใช้ Monolith เมื่อ:
- ทีมเล็ก (<10 developers)
- Product ยังไม่ stable, requirement เปลี่ยนบ่อย
- ต้องการ rapid development
- Low traffic (<10k RPM)

ใช้ Microservices เมื่อ:
- ทีมใหญ่ (multiple teams)
- Different scaling requirements per service
- Need independent deployments
- High traffic, need horizontal scaling
```

**Q2: อธิบาย CAP Theorem ใน context ของ Microservices**

```
CAP: Consistency, Availability, Partition tolerance
ระบบ distributed ทำได้แค่ 2 ใน 3:

CP (Consistency + Partition tolerance):
- ตัวอย่าง: HBase, MongoDB (strong consistency mode)
- ยอมรับ downtime เพื่อ consistency

AP (Availability + Partition tolerance):
- ตัวอย่าง: Cassandra, CouchDB, DynamoDB
- ยอมรับ eventual consistency เพื่อ availability

CA (Consistency + Availability): ไม่มี partition tolerance
- ทำได้แค่ใน single node (ไม่ใช่ distributed system จริง)

ใน Microservices เราเลือก AP ส่วนใหญ่:
- Eventual consistency via events
- BASE properties แทน ACID
```

**Q3: อธิบาย Saga Pattern และความแตกต่างระหว่าง Choreography vs Orchestration**

```typescript
// Choreography: แต่ละ service listen events และ react
// Pros: loose coupling, simple
// Cons: hard to track state, scattered logic

// OrderService
kafkaProducer.send('order.created', { orderId, items });

// InventoryService (listens)
kafkaConsumer.on('order.created', async (order) => {
  await reserveItems(order);
  kafkaProducer.send('items.reserved', { orderId: order.orderId });
});

// Orchestration: central coordinator manages flow
// Pros: clear saga state, easy monitoring
// Cons: central point of failure, more complex

class OrderSaga {
  async execute(orderId: string) {
    await this.step('reserve_inventory', () => inventoryService.reserve(orderId));
    await this.step('charge_payment', () => paymentService.charge(orderId));
    await this.step('send_notification', () => notificationService.send(orderId));
  }

  async compensate(orderId: string, failedStep: string) {
    if (failedStep === 'charge_payment') {
      await inventoryService.release(orderId); // compensating transaction
    }
  }
}
```

**Q4: How do you handle distributed transactions?**

```typescript
// Option 1: Saga Pattern (recommended)
// ใช้ compensating transactions แทน 2PC

// Option 2: Outbox Pattern (for event publishing reliability)
async function createOrder(order: Order) {
  await db.transaction(async (trx) => {
    await trx('orders').insert(order);
    await trx('outbox').insert({   // same transaction
      event_type: 'OrderCreated',
      payload: JSON.stringify(order),
      created_at: new Date(),
    });

  // Outbox processor publishes to Kafka asynchronously
}

// Option 3: Two-Phase Commit (2PC) — rarely used in microservices
// ปัญหา: slow, coordinator SPOF, not cloud-native
```

**Q5: Circuit Breaker อธิบายได้ไหม + show code**

import CircuitBreaker from 'opossum';

const options = {

### Architecture Design

**Q6: Design a notification service that handles 1M+ notifications per day**

```
Architecture:
1. API Gateway → Notification Service (REST/gRPC)
2. Notification Service → Kafka (publish to topic per channel)
3. Email Worker → Consume from kafka, call SES/SendGrid
4. SMS Worker → Consume from kafka, call Twilio
5. Push Worker → Consume from kafka, call FCM/APNs

Scalability:
- Kafka partitions = worker count (scale independently)
- Email: batch 1000/request via SES
- SMS: rate limit per provider
- Push: FCM batch API (500/batch)

Reliability:
- Dead Letter Queue for failed notifications
- Retry with exponential backoff
- Idempotency key per notification
- At-least-once delivery + deduplication

Database:
- PostgreSQL: notification records, delivery status
- Redis: deduplication cache (24h TTL)
- S3: email templates
```

**Q7: How would you design a rate limiter for an API?**

```typescript
// Token Bucket with Redis Lua (atomic operation)
const RATE_LIMIT_SCRIPT = `
  local key = KEYS[1]
  local capacity = tonumber(ARGV[1])
  local refill_rate = tonumber(ARGV[2])
  local now = tonumber(ARGV[3])
  local tokens_needed = tonumber(ARGV[4])

  local bucket = redis.call('HMGET', key, 'tokens', 'last_refill')
  local tokens = tonumber(bucket[1]) or capacity
  local last_refill = tonumber(bucket[2]) or now

  local elapsed = now - last_refill
  local refill = math.floor(elapsed * refill_rate / 1000)
  tokens = math.min(capacity, tokens + refill)

  if tokens >= tokens_needed then
    tokens = tokens - tokens_needed
    redis.call('HMSET', key, 'tokens', tokens, 'last_refill', now)
    redis.call('EXPIRE', key, 3600)
    return 1  -- allowed
  else
    return 0  -- rate limited
  end
`;

async function isAllowed(userId: string, tokensNeeded = 1): Promise<boolean> {
  const result = await redis.eval(
    RATE_LIMIT_SCRIPT,
    1,
    `rate_limit:${userId}`,
    100,   // capacity
    10,    // refill rate (tokens/sec)
    Date.now(),
    tokensNeeded
  );
  return result === 1;
}
```

### System Design

**Q8: Design an order management system for an e-commerce platform (10M orders/day)**

```
Services:
1. Order Service — create/update orders, PostgreSQL
2. Product Service — catalog, availability, MongoDB
3. Inventory Service — stock levels, Redis + PostgreSQL
4. Payment Service — charge customers, external gateway
5. Notification Service — emails, SMS, push
6. Search Service — Elasticsearch for product search

Communication:
- Sync: Order → Payment (need immediate response)
- Async: Order → Inventory, Notification (via Kafka)
- CQRS: OrderCommand DB (write) + OrderQuery DB (read replica)

Scaling:
- Orders: PostgreSQL + read replicas
- Inventory: Redis for real-time + PostgreSQL for persistence
- Product: MongoDB with horizontal sharding
- API: Horizontal scaling with Kubernetes HPA

Reliability:
- Saga pattern for order → payment → inventory
- Outbox pattern for event publishing
- Idempotency for payment (idempotency key)
- Distributed lock for inventory (prevent overselling)
```

check "Resource limits set" "kubectl get pods -n production -o json | jq '.items[].spec.containers[].resources.limits' | grep -v null"

# Observability
check "Prometheus scraping" "curl -s http://prometheus:9090/api/v1/query?query=up | jq '.status' | grep -q success"
check "Jaeger receiving traces" "curl -s http://jaeger:16686/api/services | jq '.data | length' | grep -v '^0$'"
check "Alerting rules active" "kubectl get prometheusrule -n monitoring | grep -v 'No resources'"

# CI/CD
check "ArgoCD synced" "argocd app list | grep -v 'OutOfSync'"
check "All deployments healthy" "kubectl get deploy -n production | grep -v '0/'"

echo ""
echo "Results: $PASS passed, $FAIL failed"
if [ $FAIL -eq 0 ]; then
  echo "🎉 Production ready!"
else
  echo "⚠️  Fix $FAIL issues before going to production"
fi
